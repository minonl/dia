# 配置迁移：用 LLM 任务，不写 migration 代码

> 2026-11-04。适用：dia / persona / kit 的**声明式格式**升级（`dia.json`、`lock`、`registry.json`、`deps.jsonl` 等）。
> 原则：**升级 = 改声明 + 文档；旧数据迁移交给带判据的 LLM 任务**，不在代码里堆版本分支。

## 1. 为什么

- migration 代码要长期背兼容矩阵，测试面指数增长；
- 声明式格式的迁移大多是"文本改写 + 语义校验"，正是 LLM 擅长的；
- 用任务 + 判据驱动，迁移过程本身可审计、可回滚。

## 2. 流程（每版一次）

1. **定版**：在 `docs/` 写清「旧格式 → 新格式」的对照表与判据（机器可执行命令优先）。
2. **生成迁移任务**（模板见 §3）：一个版本一个任务，**幂等**、带 `--dry-run` 演练。
3. **LLM 执行**：任务只允许改声明文件（`dia.json` / `dia.lock` / `projects/*.json`），不改代码。
4. **判据校验**：`dia persona verify <id>` + `dia doctor --persona <id>` + 目标命令自检。
5. **回滚**：迁移前 `dia persona use <id>@<old>` 或保留 `backups/`；失败即回滚，不半迁移。

## 3. 任务模板

```bash
dia task add "迁移 <persona> 到 <schema vN>" --judge "dia persona verify <id> && dia doctor --persona <id> && bun run test"
# 任务描述里必须带：
#   - 旧格式样例（脱敏）
#   - 新格式要求（字段/必填/默认值）
#   - 只允许改的文件清单
#   - dry-run 方式 + 回滚方式
```

LLM 侧执行约束（写进任务描述）：

- 只改清单里列出的文件；**不碰** 代码、`docs/`、其它 persona；
- 每步先 `--dry-run` 或 `git diff` 自证，再落盘；
- 遇到无法判定的字段 → 停，不猜；
- 完成后贴判据命令与输出。

## 4. 禁止 / 要求

| 禁止 | 要求 |
|---|---|
| 在代码里写 `if (schema === 1) ... else if (schema === 2)` 链 | schema 只做**校验**（不认识的版本直接报错） |
| 迁移脚本自动改用户数据 | 迁移必须是一次显式任务，人可见 |
| 迁移不可逆 | 先备份 + 记录旧版本指针 |
| 一次迁多个版本 | 一版一任务，逐版迁移 |

## 5. 例外

当迁移是**安全敏感**（凭据、路径越界检查）或**必须原子**（审计链格式）时，才写代码，并在本文件登记理由与判据。
