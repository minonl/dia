# H0 报告：三层架构覆盖分类实验

> 日期 2026-10-29。判据来自 `dabo-agent/docs/hypotheses.md` H0：
> “三层瘦架构（框架/入口/包）能覆盖 ≥90% 真实任务，维护成本减半。”
> 本报告只回答**覆盖**；**维护成本减半无法判定**（没有改造前基线）。

---

## 1. 结论

**按严格口径，H0 的覆盖预测未成立：17/20 = 85%，低于 90%。**

失败集中在同一类：**宿主客户端/插件/本机环境**（3 条）。它们既不属于 framework 的通用引擎，
也不属于 domain 的域内容，也不属于 kit 的可复用内容——三层里没有“宿主适配”这个承接处。

- 若把“DSH 配置页调研”算作 kit 的知识产出，覆盖率是 **18/20 = 90%**，正好卡在边界；
- 另外两条（Electron 客户端插件、本机编辑器/浏览器插件安装）仍然无归属；
- **维护成本减半**：无改造前数据，**无法判定**；只能给出代理指标（见 §4）。

**建议**：不要回到单仓单层；把“宿主适配”显式补进入口层（adapter 子层，已落到
`docs/architecture.md` §2.1）。然后按 50 样本、双人独立分类重跑；本报告只完成 20 样本严格口径。

---

## 2. 方法

### 数据

- 本机 `dia ingest sessions --full` 产出：**322 条 episode**（不是假设里的 257；旧数字已过时）。
- 过滤测试夹具（`headless`、`Implement this task`、`verify-ws`、`team-data`、`Return only JSON`、
  `You are teammate`、`YAN-OK` 等）后剩 **140 条**。
- 固定 `seed=11` 抽 20 条；样本与逐条标注见 `sample.json`。
- 复现：`bun experiments/h0-sample.ts <episodes.jsonl> 11`。

### 分类口径

| 层 | 承接什么 |
|---|---|
| framework | 与域无关的引擎能力：ingest/audit/kb/team/版本/渲染/沙箱 |
| domain | 单个入口的内容与策略：yan 工作域、dabo 个人域、宿主入口适配 |
| kit | 可复用知识/技能/工具内容；默认无执行权 |

- `fits=true`：任务能被三层之一**唯一承接**，不需要新增第四种职责；
- `framework_change=true`：任务会逼 dia 改框架代码/契约；
- `host_coupled=true`：依赖 Electron/DSH 客户端、本机编辑器/浏览器等宿主环境。

## 4. 解释

### 4.1 失败不是“分层错了”，是少了一个承接处

3 条失败全部与**宿主**有关：

- DSH 是 Electron 应用，客户端插件（Mermaid 预览、配置页）需要宿主插件代码；
- iTerm2/浏览器插件属于本机环境安装，不是 agent 的 persona/kit。

这说明三层对“agent 能力类任务”覆盖良好（17 条里 17 条有主责层），
但对“宿主集成类任务”没有位置。把这类任务硬塞进 domain，会让域仓库承担宿主 UI 代码，
维护成本反而上升。

### 4.2 “维护成本减半”没有证据

- 没有改造前/后的维护成本基线；
- 没有每个任务的 diff、变更包数、review 时长；
- 只有“70% 任务不需要改框架”这一代理指标，能说明**变更局部化**，不能证明成本减半。

### 4.3 这个结果对架构的含义

- **不要**因为 85% 就回到单仓单层——失败面很窄，且集中在宿主；
- **要**补一个明确的“宿主适配”职责（放在入口层或独立第四层），并规定：
  - 宿主插件代码不进 framework；
  - 宿主适配可以依赖 framework，但 framework 不反向依赖宿主；
  - kit 仍默认无执行权，宿主插件需显式授权。

---

## 5. 限制

1. **单评价者**：分类由我一人完成，没有双人独立标注/一致性系数；
2. **样本偏差**：全部来自本机会话，工作域/框架开发占比高；不是用户任务总体；
3. **episode 是摘要**，不是完整任务描述，分类依赖摘要信息；
4. **257 → 322**：假设里的数据版本已过时，旧样本不可复现；
5. **“fits”口径较宽**：把“能在现有能力上执行”与“有唯一主责层”分开后，结论对口径敏感（85% vs 90%）；
6. **成本未测**：没有改造前后对照。

---

## 6. 决定

| 选项 | 结论 |
|---|---|
| H0 原样支持 | ❌ 严格口径 85%，不成立 |
| 回到单仓单层 | ❌ 失败面窄，代价过大 |
| 补宿主适配后重跑 | ✅ 推荐 |
| 维护成本减半 | ⏸ 无法判定，需先埋点 |

**下一步（建议）**：
1. 在 `docs/architecture.md` 明确“宿主适配”归属与依赖方向；
2. 用 50 样本 + 双人独立分类重跑，报告 Cohen's κ；
3. 在每个 MR 记录“改动层”（framework/domain/kit/host）与变更行数，积累 4 周后再判“成本减半”。
