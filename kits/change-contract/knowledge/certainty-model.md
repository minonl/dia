# 确定性模型

> 工具链（dia / persona / 项目仓 / CI）不只是「省事」，它在提供**确定性**：
> 让环境、应用、智能体、人对同一件事有**同一个可验证的预期**。

## 1. 四类确定性

| 层 | 对象 | 不确定的表现 | 确定性来自什么 |
| --- | --- | --- | --- |
| **环境** | 机器 / 依赖 / 分支 | 「在我机器上是好的」、依赖漂移、并发会话互相踩 | 可复现：worktree 隔离、真装依赖、版本锁、幂等脚本 |
| **应用** | 产品行为 | 修了 A 坏了 B、换实现导致交互回退 | 行为契约：不变式 + 契约测试 + 对照组 |
| **智能体** | agent 的工作法 | 同一需求两次做法不同、跳过确认、按记忆走 | 工作法：分级 + 门禁 + 证据 + 留痕（本 kit） |
| **人** | 决策与责任 | 「我不知道谁同意的」、需求被引申 | 决策可追溯：需求原文 + 确认人 + 时间 + 依据 |

四层缺一层，整体就不可信：环境不稳 → 证据不可复现；应用无契约 → 改动不可预测；
智能体无工作法 → 门禁形同虚设；人无留痕 → 出了问题无法归因。

## 2. 每条确定性的三件套

任何一条「确定」都必须同时具备：

1. **不变式（contract）**：什么是不允许变的？写下来。
2. **证据（evidence）**：怎么证明它没变？可重跑、可对照。
3. **责任人（owner）**：变了谁批准？出问题找谁？

> 只有 1 没有 2 = 口号；只有 2 没有 1 = 测了个寂寞；只有 1、2 没有 3 = 无人负责。

## 3. 工具链的角色：把「靠人记得」变成「机器可见」

- **人记得**：依赖自觉，规模一大必漏（本次案例：文档写了「需 PD 确认」，仍然直接全量）。
- **机器可见**：模板必填 + CI 校验 + 灰度记录 + 台账条目。
  机器不需要理解需求，只需要验证「该有的字段有没有、该闭的项有没有闭」。

判断一个机制是否真的存在，只看一条：

> **它能不能在人不配合的时候拦住动作？**
> 拦不住 = 提醒；拦得住 = 门。

## 4. 确定性成本表（为什么不能全都要）

| 机制 | 拦得住 | 成本 | 适用 |
| --- | --- | --- | --- |
| 设计契约 diff 表 | 只拦「没想到」 | 15 min/次 | 所有 A/B 级改动 |
| MR 模板必填 + CI | 拦「想到但没写」 | 一次性脚本 + 每次 5 min | 所有改动 |
| 灰度准入 checklist | 拦「没确认就放大」 | 10 min/次 | 所有开关类变更 |
| 契约测试（对照组） | 拦「实现变了但没人知道」 | 0.5~1 天/组件 | 交互复杂、复用高的组件 |

原则：**门要少、要硬、要便宜**。十项软提醒不如一道真门。

## 5. 与变化的关系

确定性不是拒绝变化，而是让变化**可预期**：

- 需求变化 → 更新 spec/todo（拥抱变化）；
- 实现变化 → 先过契约 diff，再动代码；
- 交互变化 → 必须有人签字；
- 环境变化 → 必须可复现。

> 一句话：**变化可以快，但不能「悄悄地」快。**
