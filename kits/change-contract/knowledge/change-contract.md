# 变更契约

> 适用：**需求面小、影响面大**的改动——换数据源 / 换接口 / 加缓存、性能优化、
> 分页与排序策略、依赖或框架升级、组件替换与重构、以及任何「顺手」改动。

## 0. 问题类（这个 kit 防的是什么）

一类反复出现的失败：

> 需求很确定、变更分界也很清楚，但**混入了端到端体感强烈的变化**，结果不可预期。

它不是「写错代码」，而是**设计溢出（scope spillover）**：
实现次要目标（性能 / 接口形态）时，顺带改变了用户已经依赖的行为，
而这次改变既不在需求里，也没有人对它签字。

**判据（记这一条就够）：**

```
感知面变化 ∉ 需求面  ⇒  设计溢出
```

允许存在，但必须同时具备：**明确理由 + 有权人确认 + 回写设计 + 留痕**。
缺一条，就不是「优化」，是「未经许可的减配」。

## 1. 三个面

| 面 | 定义 | 怎么取 |
| --- | --- | --- |
| **需求面** intent | 需求原文里出现的动词与名词 | 逐字抄需求，不改写、不引申 |
| **影响面** blast radius | 实际改到的层 | 取数 / 状态 / 交互 / 文案 / 权限 / 性能 |
| **感知面** perceivable | 用户看得见、摸得着的变化 | 用第 2 节的契约字段逐项 diff |

> 需求面是**唯一**授权来源。设计文档、接口契约、技术方案都**不能**作为「用户同意」的证据。

## 2. 交互契约 8 字段（列表 / 表单 / 流程通用）

任何「换数据源 / 换实现」的改动，先填这张表；**默认值全部是「不变」**，
要写「变」必须同时写依据与确认人。

| # | 字段 | 改动前 | 改动后 | 判定（不变 / 需求内 / 溢出） | 依据 & 确认人 |
| --- | --- | --- | --- | --- | --- |
| 1 | 取数方式（全量 / 分页 / 游标 / 增量） | | | | |
| 2 | 触发方式（滚动 / 按钮 / 自动轮询） | | | | |
| 3 | 顺序与页大小（排序键、稳定性） | | | | |
| 4 | 加载态（首屏 / 追加 / 重试） | | | | |
| 5 | 结束态（没有更多 / 上限提示 / 到底） | | | | |
| 6 | 计数文案（总数 / 已加载 / 命中数） | | | | |
| 7 | 空态与错误态 | | | | |
| 8 | 搜索与筛选（是否回退、是否分页） | | | | |

**填写纪律**

- 「不变」也要写，用来证明你**看过**旧行为，而不是没想。
- 同一个组件里两种浏览方式（有关键词滚动、无关键词按钮）本身就是溢出信号。
- mockup 没写 ≠ 可以改。**沉默代表维持现状**；要改就回写 mockup 或登记偏离。
- 旧实现没写下来的行为，就是这次改动最容易丢掉的东西——先把它写进表里。

## 3. 变更分级（决定要过哪几道门）

| 级别 | 判定 | 典型例子 | 必过门 |
| --- | --- | --- | --- |
| **A 交互级** | 感知面有变化（第 2 节任一字段「变」） | 翻页手势、默认排序、空态、计数口径、搜索行为 | 1 + 2 + 3 + 4 |
| **B 数据级** | 只换取数实现，**感知面全部不变** | 换接口、换索引、加缓存、性能优化 | 1 + 2（声明「全字段不变」） |
| **C 缺陷级** | 恢复既有契约、修错误行为 | 修 bug、回退误改 | 2 + 4（需对照组） |

> 最常见的翻车方式：**A 级改动被当成 B 级做**——级别判低，门就全跳过。

## 4. 四道门

### Gate 1 · 设计：契约 diff（默认不变）

- 设计与代码**不要塞进同一个提交/同一个评审**：设计确认在前，实现在后。
- 设计文档里必须有第 2 节的表；「变」的每一行都要有结论，不能留空。

### Gate 2 · 评审：必填 + 偏离登记

- MR / PR 描述必须包含「变更影响面」：`分级`、契约表摘要、`确认人`。
- 偏离既有交互的，登记到偏离台账（仓库内 `design-drift-register` 或等价物），
  写明：改了什么、为什么、谁确认、何时回写设计。
- **模板里的勾选项必须能被机器校验**；纯自检 = 没有门。

### Gate 3 · 灰度：准入 checklist

放开开关（GrowthBook / 配置中心 / 白名单）**是高风险动作**，和发版同级：

- 改开关前记录：改动面 / 交互影响 / 确认人 / 回滚方式 / 观测指标。
- **设计文档里挂着的「待确认」没关闭 → 禁止扩量**（可灰度内测 1~3 个 org，不可 50%→100%）。
- `flag 默认关闭` 只保证「合并时零差异」，不保证「上线时零差异」。

### Gate 4 · 回归：契约测试（对照组）

- 测试要描述**用户体验**（滚到底自动追加、终态提示、计数口径），不是描述代码实现（「按钮存在」）。
- 必须带**对照组**：旧实现应当失败的新用例，才是真的回归测试。
- 结论三态：**通过 / 不通过 / 无法判定**；「无法判定」不等于通过。

## 5. 证据链（给「确定性」用的）

一条改动要能被别人复核，至少留四样：

1. **Before**：旧行为的证据（截图 / 抓包 / 旧版本产物 / 代码位置）；
2. **After**：新行为的证据（同口径）；
3. **对照组**：证明不是环境噪声（旧实现失败 / 双版本对照）；
4. **归属**：谁确认、何时、依据哪条需求或哪次沟通。

## 6. 反模式清单（看到就停）

| 反模式 | 为什么错 |
| --- | --- |
| 「接口是分页的，所以 UI 必须手动翻页」 | 分页是取数实现；触发方式是交互决策，接口不规定 |
| 「flag 默认关闭 = 安全」 | 真正的高风险动作是**改开关**，它比发版更轻、更容易绕过评审 |
| 「单测绿 = 没回归」 | 测试按设计写，只能证明「实现 = 设计」，证明不了「设计 = 用户预期」 |
| 「mockup 没写，所以可以改」 | 沉默 = 维持现状；变更需回写或登记偏离 |
| 「需求没提，但用户肯定能接受」 | 需求面是唯一授权来源；接受度要用反馈证明，不能用推测 |
| 「先灰度，灰度会发现问题」 | 灰度只能**暴露**问题，不能替代**确认**；它会让客户替你验收 |
| 「顺手一起改了」 | 顺手 = 没有需求依据 = 溢出 |

## 7. 案例：商品分组「自动添加」列表（2026-11-25，hummus）

**需求面**：客户要「商品分组能按上架时间/热度排序」。
**实际改动**：为了服务端排序接入 CK 搜索接口（offset/limit + `has_more`，无 `total`）。
**溢出**：把「滚动即可看」改成「手动点『加载更多』」，并缺失「没有更多了」终态。

| 字段 | 改动前 | 改动后 | 判定 |
| --- | --- | --- | --- |
| 取数方式 | 全量分批 | 服务端分页 | 需求内（性能） |
| **触发方式** | **滚动** | **按钮** | **溢出** |
| 顺序 | 无服务端排序 | 热度 / 上架时间 | 需求内 |
| 结束态 | 无 | 无 | **缺失** |
| 搜索行为 | 全量 + 滚动 | 全量 + 滚动 / 其余按钮 | **不一致** |

**为什么会漏**：
设计与代码同一个提交；「需 PD 确认」只是文档里一句话，不是阻塞项；
MR 模板有「设计对照」但没人填、也没人校验；灰度 50%→100% 前只查了 Redmine 报障，没回看确认项。

**教训**：`接口分页 ≠ 交互分页`。换数据源时，**只有取数方式**可以变。

## 8. 各层怎么用这个 kit

| 层 | 用法 |
| --- | --- |
| **dia** | 安装本 kit：`dia kit add --from <repo> kits/change-contract`；`cc-check` 校验变更描述 |
| **persona（yan / dabo / …）** | 把本页作为必读知识；在分级、评审、灰度场景引用；不复制正文 |
| **项目仓** | MR 模板 + CI 校验 + 偏离台账；项目特有字段追加到第 2 节，不另起一套 |

> SSOT 纪律：方法只在 kit 里维护一份；persona 只写「何时引用」，项目只写「本项目特有字段」。
