# change-contract —— 变更契约闸门

> SSOT：`knowledge/change-contract.md`（方法）、`knowledge/certainty-model.md`（为什么）。
> 本 skill 只负责**何时用、怎么走、怎么验**。

## 触发（命中任一就走）

- 换数据源 / 换接口 / 换索引 / 换存储 / 加缓存
- 性能优化，尤其是「一开始就分页/裁剪/懒加载」这类取数变化
- 分页、排序、筛选、搜索策略调整
- 依赖 / 框架 / 构建工具升级
- 组件替换、设计系统迁移、重构（哪怕「行为不变」）
- 任何带「顺手」「一起」「顺便」的改动

## 第 0 步：先判级，再动手

```
感知面变化 ∉ 需求面 → 设计溢出
```

- **A 交互级**：8 字段里有任一「变」→ 必须先确认再实现
- **B 数据级**：8 字段全部「不变」→ 可以直接做，但要在 MR 里声明
- **C 缺陷级**：恢复既有契约 → 必须带对照组

拿不准时按 A 处理。

## 第 1 步：填契约 diff（默认不变）

把 `knowledge/change-contract.md` §2 的 8 字段表抄到设计文档 / MR 描述里，
逐项写「改动前 / 改动后 / 判定 / 依据 & 确认人」。

**「不变」也要写**——它证明你对照过旧行为，而不是没想。
旧行为先写下来：它最容易在换实现时被丢掉。

## 第 2 步：机器校验

```bash
cc-check --file <设计文档或 MR 描述.md>          # 通过退出 0，缺项退出 1
cc-check --file <...> --json                    # 机器可读
cat <描述.md> | cc-check                         # stdin
```

校验内容（最小集）：

- 存在 `## 变更影响面` 段
- 有 `分级：A|B|C`
- B/C 级声明 `交互契约：不变`
- A 级必须有 `确认人：` 与 `依据：`

> 门要硬：CI 里跑它，缺项就红。软提醒等于没有。

## 第 3 步：灰度准入（A 级）

放开开关前必须写一行记录：**改动面 / 交互影响 / 确认人 / 回滚方式 / 观测指标**。

- 设计文档里挂着的「待确认」没关闭 → **禁止从内测灰度扩到 50%/100%**
- `flag 默认关闭` 只保证合并时零差异，不保证上线时零差异

## 第 4 步：回归要对照组

- 用例描述**用户体验**（滚到底自动追加、终态提示、计数口径），不是描述代码（「按钮存在」）
- 旧实现应当失败的新用例，才算契约测试
- 结论三态：通过 / 不通过 / 无法判定

## 输出模板

```markdown
## 变更影响面

分级：B   # A 交互级 / B 数据级 / C 缺陷级

| 字段 | 改动前 | 改动后 | 判定 | 依据 & 确认人 |
| --- | --- | --- | --- | --- |
| 取数方式 | 全量分批 | 服务端分页 | 需求内 | 需求：排序；性能：2 万商品 |
| 触发方式 | 滚动 | 滚动 | 不变 | — |
| 结束态 | 无 | 「没有更多了」 | 需求内（补全） | — |
...

确认人：—（B 级无需确认；A 级必须写）
```

## 常见反模式（命中即停）

- 「接口是分页的，所以 UI 必须手动翻页」——分页是取数实现，触发方式是交互决策
- 「flag 默认关闭 = 安全」——改开关才是高风险动作
- 「单测绿 = 没回归」——测试按设计写，只能证明实现符合设计
- 「mockup 没写 = 可以改」——沉默代表维持现状
- 「先灰度，灰度会发现问题」——灰度只能暴露问题，不能替代确认
